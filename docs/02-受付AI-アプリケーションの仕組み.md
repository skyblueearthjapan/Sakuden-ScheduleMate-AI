# 受付AI（reception-ai）の仕組み（調査メモ）

調査日: 2026-09-14
対象: `Documents/受付AI/reception-ai`（GitHub: skyblueearthjapan/Reception-AI、private）
正本ドキュメント: `docs/HANDOVER_2026-09-14.md`、`docs/SPEC.md`、`docs/reference/gpt-live-api.md`

## 1. 一言でいうと

新工場の受付タブレットで、来客が話しかけると **GPT-Live（OpenAI の音声会話モデル）** が応答し、
社内名簿・在席・来客予定を根拠に担当者を特定して、担当部署のインターホンへ案内するシステム。
サーバーは社内の Orange Pi 4 Pro 1 台（Fastify + PostgreSQL 16 + nginx）。

## 2. 構成（モノレポ、pnpm）

| 場所 | 役割 |
|---|---|
| `apps/web` | React/Vite。キオスク画面（来客用）とコンソール（ホーム・予定・履歴・設定） |
| `apps/edge-api` | Fastify。会話の判断、名簿、取次ぎ、記録。TypeScript |
| `apps/worker` | 定期ジョブ（在席・予約の同期、idle 終了） |
| `packages/contracts` | Zod スキーマ = API 契約の正本。OpenAPI を生成し CI でドリフト検査 |
| `packages/domain` | 純粋ロジック（名簿照合、在席判定など） |
| `database/migrations` | 0001〜0009、23 テーブル |
| `tools/codex-image` | **Codex MCP で UI 画像を生成するツール**（後述） |
| `runtime-knowledge` | AI への指示文 |

テスト: 単体 500 超 + 統合 181（PGlite）。CI は GitHub Actions。

## 3. 会話の仕組み（ここが本題）

```
ブラウザ(タブレット) ──WebRTC 音声──► OpenAI GPT-Live (gpt-live-1)
       │                                      ▲
       │ POST /voice/sessions (SDP offer)     │ sideband WebSocket（API キーはサーバーだけ）
       ▼                                      │
   edge-api ──────────────────────────────────┘
       │ 文字起こし delta を受け取り、発話境界を自前で判定
       │ 「事実欄」（名簿・在席・予定）を組み立てて
       ▼
   gpt-5-mini（Responses API、strict JSON Schema）で業務判断
       │ { text, extracted{company,name,purpose,host_name,...}, next, confirmation, ... }
       ▼
   session.commentary.append で GPT-Live に「話す内容」を注入 → 音声で来客へ
```

要点
- **音声は GPT-Live に丸投げ**。聞き取り（STT）と発話（TTS）を自前で持たない。
- **判断は 2 段構え**。GPT-Live は喋るだけで、何を言うかはサーバー側の `gpt-5-mini` が JSON で決める（`adapters/agent/openai.ts` の `REPLY_SCHEMA`）。
- 抽出項目は固定（会社名・氏名・用件・担当者名・役職・部署）。分からない項目は null。推測で埋めない。
- 会話全文は保存しない。抽出結果と判断だけを `visit_events` に記録。
- 委譲モードは `client`（アプリ側で判断）。sideband 接続で WebView を信用せずサーバーが制御する。
- セッション最大 2 時間、$0.05/分、作成だけで 15 秒分課金。日次予算で上限を設定。

## 4. 在席・予定の扱い

- 在席: Google スプレッドシート「外出記入板」を 2 分ごとに読み取り → `employee_presence`
- 予定: 「会議室予約」シートを 5 分ごとに読み取り → `appointments(source=room_booking)`
- どちらも **読み取り専用**。AI は在席や予定を「事実欄」として参照するだけで、**書き込みはしない**。
- コンソールの予定画面（`SchedulePage.tsx`）から手入力の予定は作成・更新できる（Google 由来は読取専用）。

## 5. 画像生成（Codex MCP）

`tools/codex-image/` にある仕組みで、UI 用の画像を Codex に作らせている。

- `mcp-client.mjs`: `codex mcp-server` を stdio で起動する薄い JSON-RPC クライアント（initialize → tools/list → tools/call codex）
- `generate.mjs`: `manifest.json` の画像ごとに Codex セッションを起こし、「組み込みの画像生成機能で PNG を指定パスに保存せよ」というプロンプトを渡す
- Codex 側で画像生成モデル（GPT-Image）が動き、ファイルが書き出される
- 生成物例: 受付嬢アバター（`avatar-receptionist.png`）、デモ来客写真 4 枚、ロゴ、ヒーロー背景
- 実在人物は使わず、全て架空の人物として生成

前提: `codex` CLI がログイン済みで `image_generation` 機能が有効（2026-09-14 時点で codex-cli 0.153.4、有効を確認済み）。
Windows では `codex.cmd` を shell 経由で spawn する。

## 6. 今回のスケジュールAI に流用できるもの・しないもの

| 流用する | 理由 |
|---|---|
| `tools/codex-image` の 2 ファイル（mcp-client / generate） | 人物画像の生成にそのまま使える |
| 「判断は JSON Schema で固定する」考え方 | 予定の抽出（誰・いつ・何）を確実に取り出せる |
| 「推測で埋めない、確認してから書く」規則 | DB へ誤った予定を書かないため |

| 流用しない | 理由 |
|---|---|
| GPT-Live（音声 WebRTC + sideband） | 複雑で課金が大きい。まずはテキストチャットで十分 |
| Fastify + PostgreSQL + contracts + worker の構成 | 目的に対して重すぎる |
| 名簿・在席の Google シート同期 | 所在ダッシュボードの `GET /api/staff` がそのまま名簿になる |
