## 3. 今日やったこと（時系列）

1. 所在ダッシュボードのスケジュール管理（`events` テーブル、追加/削除 API、SSE）と受付AI（GPT-Live + gpt-5-mini の 2 段構え、Codex MCP の画像生成）を調査（`docs/01`〜`02`）。本番 DB を読み取り専用で確認（`docs/04`）。
2. HTML モックを作成（Artifact）。会長限定・お弁当対応・ボタン無し・自動スクロールの順に修正。さくらの画像を GPT-Image（Codex MCP、`tools/codex-image`）で 2 回生成（制服姿を採用）。
3. 本実装: GPT-Live（WebRTC + sideband）＋ 判断 `gpt-5.6-luna`。合成音声を擬似マイクに流す通し試験 3 回、判断ロジックの通し試験（登録・訂正・取り消し・休み・連日・曜日解決）。
4. PWA（manifest、sw.js、GPT-Image のアイコン）。画面を「写真固定・一言だけ差し替わる」形にし、スマホ / PC を自動切り替え。
5. 公開: Tailscale 版（http、マイク不可）→ Cloudflare Tunnel + 配布リンクのアクセスキー（手順書 3 章を実装: `server/access.mjs`、`/api/key`、入口スクリプト、`docker-compose.prod.yml`）。Cloudflare の Tunnel/DNS 作成、VPS 配置、動作確認まで実施。
6. 会長の試用を受けて調整: つなぎ言葉（内容に合わせて変える）、お弁当の返事の幅（「お願いします」= いる）、硬い言葉の禁止（「ご入用」など）、予定の確認（先月〜3 か月先）、聞くのは外出時の「どこへ」「何の案件」だけ、お弁当を未回答に戻す、予定の変更（削除＋再登録）、時刻。
7. 所在ダッシュボードのキー方式切り替えで会話が始められなくなった（500）→ `DASHBOARD_API_KEY` 対応と、ダッシュボード不通でも会話は始まるよう修正。
8. 配布資料の材料 `docs/07`（桜井NASシステム側のエージェントが案内 HTML にまとめる）。

## 4. 決定事項（守る規則）

- **画面**: 会話は流れる chat にしない。さくらの写真は固定、最新の一言だけ差し替わる。PC は写真を左に大きく。画面は「会話」「お弁当」の 2 つだけ。設定・履歴は作らない（作りすぎ NG）。
- **確認**: 予定はボタンではなく言葉（「はい」）で確認してから登録。登録は確認への肯定のときだけ。
- **聞くこと**: 外出の予定は「どこへ（お客様名・場所）」「何の案件か」の 2 つだけ、1 回に 1 つ、1 件につき最大 2 問（サーバーが数える）。同行者・時間は言われたときだけ記録。社内・休みは何も聞かない。
- **言葉づかい**: 身内向けの丁寧語。「ご入用」「ご用件」「伺っております」「承ります」「お出かけ」は禁止。つなぎは内容に合わせて毎回変える（「はい、菱和産業ですね」など）。「少々お待ちください」の連発はしない。
- **お弁当**: 登録した日に聞く。外出・休みなら「なしでよろしいですか」、社内なら「どうしますか」。休みは聞かずに「なし」。「お願いします」「頼む」= いる。未回答に戻せる。
- **予定の書き方**: ダッシュボードの流儀「客先名/作業/同行者」。区分名や「さん」は入れない。略記 社＝社長、和＝和俊、富＝富樫、千＝千葉、倉＝倉西。
- **データ**: 予定の正本はダッシュボード。SQLite に直接書かない（API 経由でないと SSE 通知が飛ばない）。会話全文は保存しない。
- **API**: OpenAI キーはこのアプリ専用（2026-09-19 から。受付AIは旧キーのままでよい＝ユーザー指示。旧キーは受付AIが使うので無効にしない）。会話 `gpt-live-1`、判断 `gpt-5.6-luna`（gpt-5-mini ではない。ユーザー指定）。
- **公開**: Tailscale ではなく Cloudflare Tunnel + 配布リンク方式（他アプリと同じ）。マイクは https 必須。
- **共有 VPS**: 他コンテナの stop/rm、`docker system prune`、`apt upgrade`、`reboot`、ufw 変更は禁止。

## 5. 残タスク・気になる点

| 区分 | 内容 | 対応案 |
|---|---|---|
| 本番設定 | `VOICE_DEBUG_TEXT=true` のまま（会話の書き起こしがログに出る） | 試用が落ち着いたら `.env` を `false` にして `docker compose -f docker-compose.prod.yml --env-file .env up -d api` |
| 配布 | 案内 HTML（QR・リンク）は桜井NASシステム側のエージェントが作成中。材料は `docs/07` | 完成後、会長・事務へ配布。一斉切り替えの用紙にも追加 |
| 会話 | 会長の実声での聞き取り精度（客先名の表記ゆれ）は未評価。客先名の一覧を事実欄で渡している | 誤りが出たら `docs/06` の「聞き取りの参考」の仕組みを拡張（読み仮名など） |
| 会話 | Live のつなぎ言葉はアドリブ。硬い・くどい文が出たら `server/prompts.mjs` の `liveInstructions` を直す | 会長の指摘文をそのまま規則に足す運用 |
| 予定の変更 | ダッシュボードに更新 API が無いため、変更は「削除＋再登録」（id が変わる、作成日時が新しくなる） | 必要なら sakurai-dashboard 側に PATCH を追加 |
| お弁当の通知 | 事務への通知は無し（ボードを見る運用）。「前日 15 時までに未回答なら聞く」は未実装 | 要望が出たら LINE WORKS 等へ通知を追加 |
| 予算 | 音声 60 分/日（≒ $3）、1 回 10 分で自動終了。実績は `/api/state` の `voice.minutes_today` | 使い方に応じて `.env` で調整 |
| ダッシュボード | `DASHBOARD_API_KEY` はダッシュボードの「管理」キーを流用。ダッシュボード側でキーを差し替えたら、こちらの `.env` も更新が必要 | 専用ラベルのキーをダッシュボード側に作ると安全 |
| 認証 | `/api/*` はアクセスキー必須。静的ファイル（画面・画像）は公開のまま（手順書どおり） | |
| iPhone | Safari で会話できることは会長が確認済み。ホーム画面追加（Safari の共有 → ホーム画面に追加）は未確認 | |
| 試験 | 実装のテストは scratchpad の使い捨てスクリプトで行った（リポジトリには無い）。`docs/06` に手順の要点 | 必要なら `tests/` に移す |

## 6. よく使う手順

```bash
# 開発 PC（Git Bash）。リポジトリ直下で
node --check server/index.mjs                          # 構文確認
# 判断ロジックだけ試す（ダッシュボードのサンドボックス: 所在ダッシュボード/app/backend で
#   SD_DB_PATH=<コピー> python -m uvicorn app.main:app --port 8000 を起動しておく）
DASHBOARD_API_BASE=http://127.0.0.1:8000/api DATA_DIR=/tmp/x node -e "import('./server/flow.mjs').then(...)"

# VPS へ反映（server/ か web/ を直したとき）
tar -czf - server web | ssh root@72.60.211.213 'cd /opt/sakuden-schedulemate && tar -xzf - && docker compose -f docker-compose.prod.yml --env-file .env up -d --build api'
ssh root@72.60.211.213 'docker logs --since 10m ssm-api | grep -v "GET /api/state"'

# 動作確認（ブラウザ相当の UA が要る）
UA="Mozilla/5.0 (Linux; Android 14) Chrome/128 Mobile"
curl -sS -A "$UA" https://schedule.sakuraidenso.net/api/health                     # {"ok":true,"dashboard":true}
curl -sS -A "$UA" -H "X-App-Key: <会長のキー>" https://schedule.sakuraidenso.net/api/state

# 止める / 戻す
ssh root@72.60.211.213 'cd /opt/sakuden-schedulemate && docker compose -f docker-compose.prod.yml down'
```

会話の中身を直すときは `server/prompts.mjs` だけを見ればよい（Live の指示 `liveInstructions`、判断の規則 `decisionInput`、出力スキーマ `DECISION_SCHEMA`、事実欄 `factsBlock`）。

## 7. ユーザー（今泉さん）の意向・進め方

- 作り方は「めちゃくちゃシンプルに」。画面や機能を増やさない。
- 会話の言葉づかいに敏感。硬い敬語は嫌う。会長の指摘はそのまま文で伝えてくるので、それを規則に足す。
- 秘密はチャットに貼らず、ファイルと VPS に置く。リポジトリは private のまま。
- 各工程で「変更・確認結果・残り」を報告し、デプロイ → コミット → プッシュまで一続きで行う。
- 桜井NASシステム側（別エージェント）が Cloudflare・配布・一斉切り替えを担当。こちらはアプリのコードを担当。
