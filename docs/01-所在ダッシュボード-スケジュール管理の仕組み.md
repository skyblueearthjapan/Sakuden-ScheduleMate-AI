# 所在ダッシュボード スケジュール管理の仕組み（調査メモ）

調査日: 2026-09-14
対象: `Documents/SDプランニング/所在ダッシュボード/app`（GitHub: skyblueearthjapan/sakurai-dashboard）

## 1. 全体構成

| 層 | 技術 | 備考 |
|---|---|---|
| フロント | React 18 + Vite（PC版 `Dashboard.jsx` / モバイル版 `MobileApp.jsx`） | nginx が `/api/` を API へプロキシ |
| API | FastAPI + SQLAlchemy 2.0 + sse-starlette | uvicorn 単一ワーカー（SSE がプロセス内バスのため） |
| DB | SQLite 1 ファイル（`/data/db.sqlite`、環境変数 `SD_DB_PATH`） | Docker volume `./data:/data` |
| 配信 | docker-compose + cloudflared（Cloudflare Tunnel / Access） | 認証は Cloudflare Access のメール許可リスト |

## 2. データモデル（`backend/app/models.py`）

```
staff (スタッフ = 所在ボードの1行)
  id            VARCHAR(8)  "S001" 形式（採番はサーバ側 next_staff_id）
  name, role    role は 代表/営業/技術/工事/事務
  status        外出中/移動中/在席/休み/直帰
  place         JSON  {pref, city} または {special: "office"|"off"}
  client        "いま何をしている"（お客様/案件/用件の自由テキスト）
  back          JSON  {type: none|undecided|jikitatsu|today|after_today, time?, date?}
  memo, completed_at, sort_order

events (予定カレンダーの1件)  ※ staff 1 : N events
  id         "ev" + hex12（サーバ採番）
  staff_id   FK → staff.id  ON DELETE CASCADE
  date       "YYYY-MM-DD"  文字列で保持（TZ ずれ回避のため Date 型を使わない）
  end_date   "YYYY-MM-DD" | NULL  連日予定の終了日（開始日以前なら NULL に正規化）
  title      最大120文字
  time       "HH:MM" | NULL
  kind       訪問/工事/社内/休み/その他
  created_at

attachments (添付メタ情報のみ。実ファイルは保存しない)
```

ポイント
- 予定は「開始日・終了日・時刻(任意)・用件・区分」の 5 項目だけ。終了時刻・場所・参加者・繰り返しは持たない。
- 連日予定は 1 レコード。上限 90 日（`MAX_SPAN_DAYS`、フロント `calendarCore.js` と一致）。
- 1 スタッフあたり予定は最大 500 件（`MAX_EVENTS_PER_STAFF`）。
- 検証は Pydantic `EventIn`（実在日付チェック、`extra=forbid`）。

## 3. API（`backend/app/main.py`）

| メソッド | パス | 用途 |
|---|---|---|
| GET | `/api/staff` | 全スタッフ（events / attachments を埋め込んで返す） |
| POST / PATCH / DELETE | `/api/staff[/{id}]` | スタッフ作成・部分更新・削除 |
| POST | `/api/staff/{id}/events` | 予定追加 `{date,endDate?,title,time?,kind}` |
| DELETE | `/api/staff/{id}/events/{event_id}` | 予定削除 |
| GET | `/api/events` | SSE ストリーム（`staff.updated/created/deleted/reset/resync`） |
| POST | `/api/reset` | シードデータへ初期化 |

- 予定の **更新 API は無い**（削除→再追加のみ）。予定 ID 単位の GET も無い。
- 予定を書き込むと、そのスタッフの全オブジェクトが `staff.updated` として SSE で全クライアントに再配信される。
- CORS は `*`、API 自体に認証は無い（Cloudflare Access が前段で守る前提）。

## 4. フロント側の仕組み

- `useStaff.js`: 初回 `GET /api/staff` → 以後 SSE で差分反映。切断検知で自前再接続、2 回目以降の `hello` で全件再取得。
- `calendarCore.js`: 純ロジック（月行列生成、連日予定の展開、週内スパンバーのレーン割当、当日予定抽出 `calEventsOn`）。
- `Dashboard.jsx`: 今日の予定チップをボード行に表示。予定の用件を「いま何をしている」(`client`) へワンクリック反映（`applyEventToClient`）。
- 予定の入力 UI は `Calendar.jsx` の `MemberCalendarPanel`（日付選択 → 用件 / 区分 / 時刻 / 終了日）。

## 5. 連結時の注意点

1. **DB は SQLite 単一ファイル**。別プロセスから直接書くと SSE 通知が飛ばず画面が更新されない。連結は **HTTP API 経由**が安全。
2. API に認証が無い（Tunnel 内前提）。外部システムから叩くなら、同一 Docker ネットワーク（`sakurai-dashboard-internal`）に同居させるか、API キー等を追加する必要がある。
3. 予定更新 API が無いので、AI 側で「予定の変更」を扱うなら DELETE + POST で代替するか、`PATCH /api/staff/{id}/events/{event_id}` をダッシュボード側に追加する。
4. 予定は「誰の予定か」が `staff_id` で決まる。会話から人物を特定して `S001` 形式の ID に解決する必要がある（名前 → ID の対応は `GET /api/staff`）。
5. ローカルの `app/data/db.sqlite` はカレンダー機能追加前のもので `events` テーブルが無い（起動時 `create_all` で自動作成される）。
